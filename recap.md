guarani/types.py   defines all Python dataclasses and enums that mirror the Coq grammar types, each with a to_coq() method that serialises the object into the exact Coq constructor string; covers orality, person, number, inclusivity, possessive markers, demonstrative proximity, verbal suffixes with their slot numbers and surface allomorphs, verb classes, transitivity, voice, mood, polarity, irregular verb paradigms, noun root classes, adjectives, postpositions, NP variants, the sentence-level SentenceType/InterrogParticle/WordOrder enums, and the adverbial-clause AdvClause/AdverbialSentence types; used by every other Python module as the shared type layer

guarani/analyzer.py   implements the morphological analyzer that inverts the prefix and suffix tables to recover a parsed ConjugatedVerb or NP from a raw surface token; loads verb, noun, adjective, and negative-pronoun lexicons from CSV; runs a recursive suffix-stripping search over all three verb conjugation classes (Areal, Aireal, Chendal) and a multi-token NP span search covering bare nouns, pronouns, possessor-noun pairs, demonstrative-noun pairs, noun-adjective pairs, and cardinal-numeral-noun pairs; derives mood (Indicative vs Imperative) from whether an imperative-modalizer suffix was stripped, via _mood_for(); tries every voice prefix (Passive je-/ñe-, Reciprocal jo-/ño-, Coactive mbo-/mo-, Objective ro-, Obj_Guero guero-, Subsuntive poro-, plus plain Active) between the person prefix and the root via _voice_attempts(), filtering wrong guesses the same way wrong negation/prohibitive guesses are filtered — by lexicon lookup failing; parse_guarani_num inverts Numbers.v's render_num as a 4-layer recursive-descent parser; _strip_nominal_suffixes/_noun_readings invert NP_Suf/NP_Suf2's render_np the same way _strip_suffixes does for verbal suffixes, trying every noun-headed span's final noun token (or numeral+noun's noun) both bare and with 1-2 nominal suffixes stripped, validated against suffix_pair_ok for the 2-suffix case; analyze_chendal_pair and analyze_prohibitive_pair handle two-token verb pivots where a Chendal person marker or the "ani" prohibitive particle is written as a separate word from the verb; returns ranked ParseResult and NPParseResult lists; depended on by both check.py and loop.py to build sentence ASTs before verification

guarani/verifier.py   wraps coqc to check whether a Sentence/AdverbialSentence AST is well-formed; serialises the AST to a Compute wf_sentence/wf_complex (...). term, writes it to a temp file, runs coqc -R against the rocq/ library, parses the boolean result, and if false runs each factored predicate individually (including ss_hierarchy_ok, which is wired into the PREDICATES list) to identify the first failing constraint; builds a natural-language feedback string from a template and returns a VerifierResult; verify_candidates accepts the best-progressing parse among several ambiguous candidates and is now what both check.py's main() and loop.py's run_loop call; the central bridge between Python and Coq. COQ_PREAMBLE now explicitly `Require Import Numbers` alongside Syntax/noun_phrases/verb/sentence — noun_phrases.v only Require Imports (not Exports) Numbers, so GuaraniNum's constructors (GN_Small, S1000_Sa, ...) aren't visible to a file that only imports noun_phrases; any NP_Num term failed to type-check with "reference not found" until this was added.

guarani/loop.py   the shared sentence-building layer plus the generate-verify-correct orchestration loop. (2) the h-form 'u paradigm — turned out to only ever apply to ACTIVE voice in the first place (coqc: render_verb for 'u at 1sg Active is "a'u", not "ha'u" — the h-form is a real-world hiatus-resolution spelling with no correspondence in the formal render function at all); non-Active voice on 'u uses the plain compositional form ("aje'u" for Passive), which the existing main-loop _voice_attempts() already parses correctly with zero additional code — verified "aje'u" -> voice=Passive worked immediately. (3) The one real gap, Chendal 3sg h/r-alternation, needed real code: coqc confirmed render_verb produces "hiresarái" (compositional, Active) vs "hesarái" (contracted, real-world spelling) for the same underlying term, and — critically — checking the actual lexicon found only one real VRoot_Relational entry ("resarái", Chendal), which stores the root WITH its r- already included as part of the word itself (not "esarái" + a separately-added r-), and confirmed via coqc that inserting a voice prefix produces "hijerresarái" for Passive (double-r artifact, from rel_pfx's own "r" plus the root's own leading "r" — this really is what the formal model computes for this particular lexicon entry). Added a new block in analyze()'s Chendal-3sg branch, gated to only fire when a non-Active voice was stripped (Active still exclusively goes through the existing contracted "chendal_h3" branch, since that's the only attested spelling for the no-intervening-voice case) — verified "ijerresarái" -> voice=Passive, well-formed against coqc.

Numerals — the "bare numeral with no noun" half of this gap turned out to be correctly unsupported, not a bug: there is no guarani_np constructor that takes just a GuaraniNum with no noun (NP_Num always pairs one with a noun), so nothing needs building there. The multi-token-multiplier half was real: S1000Su_MultSu/GN_MultSua's multiplier types (Sub1000/Sub1000Su respectively) can themselves span multiple tokens (e.g. 121,000 = "sa mokõipa peteĩsu", multiplier "sa mokõipa peteĩ" = 121 with "su" fused onto only its last token), but the parser only ever tried a single-token multiplier. Replaced _parse_sub1000_single_token/_parse_sub1000su_single_token with a general _find_fused_multiplier helper that searches increasing-length spans for one whose last token carries the fused suffix, tries parsing the whole (modified) span via the appropriate sub-parser, and requires it to consume the span exactly — used for both the "su" (thousands) and "sua" (millions) fused-multiplier cases (the "sa"/hundreds case doesn't need this, since Mult is inherently a single digit, not itself recursive). Verified three round-trips through coqc's own render_num (121,000 / 221,000 / 100,000,000) and one end-to-end sentence ("ajogua sa mokõipa peteĩsu kavaju").

Nominal suffixes on NP_Adj — render_np(NP_Adj) = noun ++ " " ++ adj, so the adjective, not the noun, is the suffix-bearing final token (e.g. "kavaju guasuete" = "a very big horse", NS_Super on the adjective). Added _adj_readings (mirroring _noun_readings, using _adj_get instead of _noun_get) and wired it into the NP_Adj branch of analyze_np_span, plus extended _is_known_non_verb's fallback to also check it (same false-positive "not in the dictionary" note that nominal-suffixed nouns needed suppressing earlier this session). Verified against coqc with "kavaju guasuite" (NS_Super, homograph-free test used porãite specifically to rule out guasu's noun-homograph "deer" reading masking the result).

Content questions in subordinate clauses — _build_subordinate_sentence (loop.py) wasn't passing has_interrog_arg to sentence_type_for at all. Fixed by computing it from the clause's trailing-argument NP before calling sentence_type_for, mirroring the fix already made to build_sentence/build_candidate_sentences earlier this session. While fixing it, found check.py's own _build_subordinate_candidates (the richer multi-candidate version) had an even bigger version of the same gap — it never set sent_type/interrog at all, defaulting every subordinate clause to ST_Declarative regardless of mood or content — fixed that too, computing sentence_type_for per (verb, arg) candidate. Verified against coqc with "aha ahecha haguã máva" ("I go [in order] to see who") — the subordinate clause correctly gets ST_Interrog_Content, and run_loop accepts the sentence.

Ditransitive IO, two sub-fixes — (1) standalone postposition token: _ditransitive_io_candidates (check.py) and the inline logic in loop.py's build_sentence only recognized =pe/=me fused onto one token (e.g. "mitãme"); added the standalone-token case ("mitã me", two words, mirroring how _postp_candidates already handles postp_comp) to both. (2) disambiguation: reordered check.py's candidate generation so the ditransitive IO/DO split candidates are tried BEFORE the plain-fallback direct_obj candidates for the same verb pivot — previously the fallback (which swallows the whole object span into one bogus NP) could still pass ss_transitivity_ok (Ditransitive only rejects "None dir_obj + Some indir_obj", not "dir_obj only") and win the first-match race ahead of the actually-correct IO/DO split. Verified against coqc: "amombe'u mitã me kavaju" now produces the correct split (DO=kavaju, IO=mitã) as its FIRST candidate, and re-verified the same for the pre-existing fused case ("mitãme") to confirm the reordering fixed it too.

Fronted object + trailing indirect object together — the fronted-object fix from earlier this session only fired when nothing followed the verb. Extended both check.py (reusing io_splits, restricted to splits whose do_span comes back empty — i.e. the whole obj_span is consumed by the IO marker, so there's no second, conflicting direct object — plus the analogous postp_comp version for Transitive verbs, since ss_postp_obj is left free for them to hold an adjunct alongside a direct object) and loop.py's build_fronted_object_sentence (which previously just returned None whenever anything followed the verb; now checks whether that trailing span is cleanly a dative pronoun or a =pe/=me-marked NP before combining it as indirect_obj). Verified against coqc: "kavaju amombe'u ndéve" ("I tell you the horse", noticia fronted, ndéve trailing dative) — well-formed in both check.py and loop.py/run_loop.

Full regression sweep re-run after each fix in this round; no prior behavior changed for any previously-passing test sentence.


Next Goals — audited against current code, 2026-08-24, updated 2026-08-25

These were checked against the actual Python source, not assumed from the Coq side, so this list supersedes any earlier version of this section:

1. CS_Counterfactual is unsatisfiable in the current Coq formalization, confirmed empirically via coqc — not just "no Python builder yet." wf_counterfactual_main requires the main clause's verb to carry BOTH VS_ObligVaera and VS_FutNegMoa, but cv_tense_ok (part of wf_conjugated_verb, hence part of wf_sentence) counts both of those among six mutually-exclusive "tense slot" suffixes and requires at most one — so wf_sentence(main) is false whenever wf_counterfactual_main is true, for any verb, any polarity, any other field. Test: mkConjVerb ... Negative Active [VS_ObligVaera; VS_FutNegMoa] None gives wf_counterfactual_main=true but cv_tense_ok=false, wf_conjugated_verb=false. A Python builder would never be able to produce a well-formed candidate no matter how it's written, so building one isn't worthwhile until the Coq side (verb.v's cv_tense_ok or sentence.v's wf_counterfactual_main) is fixed — that fix is out of scope for this Python-analyzer work.

2. Non-verbal sentences (added earlier this session) can get combinatorially large for longer inputs, since build_nonverbal_candidates tries every two-way split of the token span through analyze_np_span (itself already broad) times 3 constructors, plus the whole-span case times 2 more — fine for the short test sentences this has been exercised on, not benchmarked for longer ones.

3. Diagnosis is noticeably slower than before this session, as a side effect of generating more candidates per sentence overall (numerals/pronouns/NP_Gen/coordination/non-verbal/ditransitive IO/fronted-object/voice/multi-token-numerals/adjective-suffixes all add candidates across the two audit rounds). A failing candidate triggers a full sequential coqc predicate trace (up to ~19 subprocess invocations) for diagnosis, so a sentence with several plausible-but-wrong candidates can take 30-90+ seconds where it used to have fewer to walk through — confirmed multiple times this round on "avave oguata" specifically, still correctly returns False every time, just slowly. Not a correctness issue, but worth batching (e.g. one coqc invocation computing all predicates at once instead of one per query) if interactive latency matters — this is now the single biggest usability gap in the tool.

4. The "first well-formed candidate wins" ordering issue is only fixed for the one case that was specifically reported (ditransitive IO/DO splits vs. the plain fallback). The same underlying pattern still exists elsewhere and is only cosmetic/non-blocking (the SENTENCE still correctly verifies True either way) but can pick a less-meaningful internal parse: the "ha"/"mba'e" lexicon homographs noted earlier this session are the clearest examples, and there may be others wherever a fallback NP reading structurally overlaps with a more specific one. Not chased further since it never changes the True/False verdict, only which internal parse gets shown as "winning."

5. Fronted-object + trailing-IO (this round's fix) only handles a trailing span that is cleanly just the IO marker (a dative pronoun, or a single =pe/=me-marked token, fused or standalone) — it doesn't try a trailing span that's a multi-token IO NP (e.g. a possessed or suffixed IO noun) alongside a fronted object. Also doesn't try a fronted INDIRECT object (only direct objects front in the current implementation) — real Guaraní can front either argument for emphasis.

6. The Chendal h/r-alternation voice fix (this round) was verified against the lexicon's one actual VRoot_Relational entry ("resarái"), whose word field happens to already include its own r-. If a future lexicon entry stores a relational root WITHOUT the leading r- baked in (i.e. matching the "esarái" shape the code comments originally assumed), the new voice-intervening branch's r-stripping logic (which strips exactly one leading "r" from the voice-stripped remainder before lookup) would need re-verification against coqc for that shape specifically — the fix was derived from and tested against the real data, not the hypothetical bare-root shape.
