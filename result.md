# Grammar-Context Ablation — Implementation + Smoke Test Results

Date: 2026-09-07 (§1–§7, initial smoke test); updated 2026-09-08 (§8 Experiment 2,
§9 Experiment 3).
Model tested: `deepseek-chat` (DeepSeek API, pay-as-you-go)
Sample: 20 hand-written Spanish sentences (`data/smoke_sentences.txt`), each run under both context conditions.

---

## 1. What was built

Goal: add a `--context {none,coq}` mode that optionally injects the project's Coq
grammar definitions into the LLM's translation prompt, so the research design can
compare three conditions:

| Condition | Flag | What it measures |
|---|---|---|
| A — baseline | `--context none` | LLM only, no grammar exposure |
| B — ablation | `--context coq`, first-try only | Passive grammar exposure, no symbolic feedback |
| C — main | `--context coq`, with correction loop | Passive exposure **+** verifier feedback |

Condition B doesn't need a separate flag/run: it's recovered from a C run by filtering
to `iterations_used == 1` (accepted on the first try, i.e. what would have happened
with `max_iterations=1`), since the loop breaks immediately on acceptance regardless
of the cap. `analyse_results.py`'s "1st-try" column *is* condition B.

### Files

- **`guarani/coq_context.py`** (new) — `load_coq_context(coq_dir)` reads the Coq
  grammar files in dependency order and extracts only definitional lines
  (`Inductive`/`Definition`/`Fixpoint`/`|`/`End`/`Module`/`Record`/`Notation`),
  dropping proof scripts, tactics, and comments.
- **`guarani/loop.py`** — added `context_mode`/`coq_context` params to
  `run_eval_sentence`/`run_batch_eval`, a one-time-cached `load_coq_context_once()`
  (mirrors the existing one-time lexicon loading), and `context_mode: str` on
  `EvalResult`.
- **`guarani/run_ai_eval.py`** — added `--context {none,coq}` CLI flag (default
  `none`).
- **`guarani/analyse_results.py`** — added per-context-mode acceptance/correction
  breakdown, per-context predicate-frequency tables, and a `context_mode` column on
  the blind-rating CSV export.


## 2. Exact prompts used

**Translation prompt** (`TRANSLATION_PROMPT_TEMPLATE`, both conditions):
```
Translate the following Spanish sentence into Guaraní. Output only the Guaraní translation, nothing else.

Spanish: {spanish}
```

**Context prefix** (`CONTEXT_PROMPT_PREFIX_TEMPLATE`, prepended only when
`--context coq`, only on the *first* translation call — not repeated on correction
turns, since each `llm_fn` call is a stateless single-shot completion with no chat
history):
```
You are a Spanish-to-Guaraní translator.

The following Coq definitions specify the formal grammar for well-formed Guaraní.
Use them to guide your translation:

<coq_grammar>
{coq_context}
</coq_grammar>

```
`{coq_context}` is ~34.5 KB / ~960 lines of extracted Coq definitions from all 5
grammar files (`Syntax.v`, `Numbers.v`, `verb.v`, `noun_phrases.v`, `sentence.v`),
e.g. the opening of the `Syntax.v` section:
```
(* === Syntax.v === *)
Inductive orality : Type :=
  | Oral
  | Nasal.
Inductive person : Type :=
  | First
  | Second
  | Third.
...
```

**Correction prompt** (`CORRECTION_PROMPT_TEMPLATE`, same in both conditions, used
on every iteration after the first if the verifier rejects the output):
```
The following Guaraní sentence has a grammatical error:

  sentence: {sentence}

Error: {feedback}

Please produce a corrected version of the sentence. Output only the corrected Guaraní sentence, nothing else.
```
`{feedback}` is the natural-language message generated by `verifier.py` for
whichever of the 19 well-formedness predicates failed first (e.g. *"Transitivity
error: 'X' is Intransitive but the sentence object structure doesn't match."*).

`max_iterations=3` (default), `temperature=0.3`, `max_tokens=512` for both
conditions.

## 4. How the run actually happened (including the dead ends)

1. Implemented and unit-tested `coq_context.py` in isolation (printed the extracted
   grammar, confirmed no `Proof.`/`Qed.`/comment lines leaked through).
2. Wired context mode through `loop.py`/`run_ai_eval.py`/`analyse_results.py`,
   verified with a fake `llm_fn` that the `<coq_grammar>` block appears in the
   prompt iff `context_mode="coq"`, and that `context_mode` lands in the JSONL.
3. First real attempt: `gemini-3.6-flash`, 20 sentences, `--context none`. Hit a
   429 **per-minute** quota (free tier: 5 requests/min) after 6 sentences.
4. Retried slower (1 worker, 15s delay) — before it finished, tried batching all 20
   translations into a single request instead (per your suggestion) to cut request
   count. First batch attempt truncated (default 512 max_tokens too small for 20
   translations) and didn't follow the requested numbered format.
5. Fixed the batch prompt (4096 max_tokens, explicit format example) and retried —
   hit a 429 **daily** quota instead (free tier: 20 requests/day total, already
   spent by steps 3–4). Tried `gemini-3.1-pro-preview` as a fallback — that model
   has **0** free-tier quota (paid-plan only).
6. Stopped and asked; you funded the DeepSeek key with $2. Verified the key with a
   1-token test call, then ran the **actual production CLI**
   (`python -m guarani.run_ai_eval`) normally — DeepSeek is pay-as-you-go, so none
   of the batching workaround was needed; 3 workers, 0.5s rate-limit delay, all 20
   sentences × both conditions completed cleanly in under a minute each.

Two junk artifacts from the failed Gemini attempts (`results/smoke_none.jsonl` with
6 partial rows, `results/batch_none.jsonl` with 20 empty `BATCH_PARSE_ERROR` rows)
were deleted before the real run to avoid confusion. The `results/` files referenced
below are all from the successful DeepSeek run.

## 5. Results

### 5.1 Acceptance rates

| Context | Total | 1st-try (Condition B) | Corrected (feedback adds) | Overall (Condition A/C) | Avg iterations |
|---|---|---|---|---|---|
| `none` (A) | 20 | 8 (40.0%) | +5 (25.0%) | **13 (65.0%)** | 2.00 |
| `coq` (B→C) | 20 | 16 (80.0%) | +2 (10.0%) | **18 (90.0%)** | 1.35 |

Matches the hypothesized direction (A < B < C): passive grammar exposure alone
doubled first-try well-formedness (40%→80%), and the symbolic feedback loop closed
most of the remaining gap in both conditions. Interesting secondary observation:
the verifier feedback loop recovered **+25pp** in the no-context condition but only
**+10pp** on top of grammar context — i.e. in this small sample, symbolic feedback
and passive grammar exposure look like they're fixing overlapping error classes,
not fully additive ones. (Sample size is far too small to treat this as more than a
hypothesis worth checking at scale.)

### 5.2 Failure predicate frequency

| Predicate | `none` (27 total failures) | `coq` (9 total failures) |
|---|---|---|
| `PARSE_ERROR` | 13 (48.1%) | 3 (33.3%) |
| `ss_transitivity_ok` | 9 (33.3%) | 5 (55.6%) |
| `ss_agree_ok` | 5 (18.5%) | 1 (11.1%) |

`PARSE_ERROR` isn't a grammar-predicate failure — it means the Python
tokenizer/analyzer (`analyzer.py`, fixed lexicon) couldn't identify a verb/structure
in the LLM's output at all, so it never reached the Coq verifier. It dropped from
the single largest failure category (48%) to third (33%) under grammar context, but
it's a confound worth separating out explicitly (see §6).

## 6. Findings worth flagging before trusting this signal

**A grammatical sentence isn't necessarily the right sentence.** The Coq verifier
only checks well-formedness, not adequacy — and this sample already surfaces two
cases where the `coq` condition produced a *fluent, grammatically accepted, but
semantically wrong* translation:

- "Yo compro un caballo." (I buy a horse) → `aikuaa peteĩ kavaju` — `aikuaa` means
  "I know", not "I buy". Accepted on the first try.
- "Los niños duermen en la tarde." (The children sleep in the afternoon) →
  `Ta'anga kuéra oke ka'aru` — `ta'anga` means "image/picture", not "children".
  Accepted on the first try. (The `none` condition got this one right:
  `Mitãngue oke ka'aru`.)

Both are perfectly well-formed Guaraní sentences about the wrong thing. If the
`coq` condition tends to produce more of these than `none`, an evaluation that only
measures verifier acceptance would report `coq` as strictly better while actually
producing worse translations. This is the single most important gap to close before
running a real batch — see §7.1.

## 7. Suggested improvements before a "real" evaluation

### 7.1 Add an adequacy/fidelity check — highest priority

The verifier answers "is this grammatical Guaraní?", never "does this mean what the
Spanish said?". Two concrete additions:
- **Automatic**: back-translate the Guaraní output to Spanish with a separate LLM
  call (or use a multilingual embedding similarity score) and log an adequacy
  score alongside `accepted`, so acceptance-rate deltas can be checked against
  adequacy deltas.
- **Human**: `export_rating_csv()` currently collects `grammaticality_a/b` and
  `naturalness_a/b` but no adequacy/fidelity column — add one. Otherwise a rater
  blind to which output is which has no way to catch the `aikuaa`/`kavaju`-style
  errors above.

### 7.2 Separate `PARSE_ERROR` from real grammar failures in reporting

`PARSE_ERROR` (48% of `none`'s failures here) reflects the Python analyzer's fixed
lexicon/pattern coverage, not a grammar violation the Coq verifier judged — it's a
tooling artifact, and it's disproportionately likely whenever the LLM uses a word
or construction outside `data/merged.csv`. Report "acceptance rate among
successfully-parsed candidates" as a separate column from raw acceptance, so
context-mode deltas aren't partly just "grammar context nudges the model toward
already-lexicon-covered vocabulary."

### 7.3 Scale up sample size and pre-register sentence categories

20 sentences / 1 model is enough to confirm the plumbing and see a plausible
direction, not enough to trust the effect size. For a real run:
- 100+ sentences, stratified across the 19 verifier predicates so each grammar
  rule (inclusivity, negation, person-hierarchy portmanteau prefixes ro-/jo-,
  postposition =pe/=me on human NPs, hikuái agreement, numeral/plural agreement,
  etc.) gets deliberate coverage instead of relying on whatever a small random
  sample happens to hit.
- Multiple samples per (sentence, model, condition) at the existing
  `temperature=0.3` to estimate within-condition variance, not just one draw.
- Report paired significance (McNemar's test, since the same 20 sentences run
  under both conditions here — that pairing is already the right design, just
  needs a real n and a real test rather than eyeballing percentages).

### 7.4 Cover the full model comparison set

`LLM_REGISTRY` currently only has DeepSeek and Gemini backends. The project's own
default comparison set (`claude-opus-4-6`, `gpt-4o`, `deepseek-chat`,
`gpt-3.5-turbo`, `gemini-1.5-pro`) needs OpenAI and Anthropic `make_*_fn()`
factories added before that comparison is possible at all.

### 7.5 Per-predicate correction-success breakdown

`analyse_results.py` reports overall correction success but not *which* predicates
the feedback loop is good vs. bad at fixing. Worth adding: for each predicate that
appears as a first-iteration failure, what fraction converge by iteration 3? Some
feedback messages (e.g. transitivity) may be much clearer to the LLM than others
(e.g. person-hierarchy portmanteau prefixes), and that's directly actionable for
improving the correction prompt template per-predicate.

### 7.6 Formalize the batched-translation path for rate-limited providers

The ad hoc single-request batch-translate workaround (used mid-session to dodge
Gemini's free-tier quota) isn't in the codebase — if free-tier Gemini/other
low-quota providers need to be in the model comparison set, it's worth adding a
real `--batch-translate` mode to `run_ai_eval.py` (one LLM call translates N
sentences at once via a numbered-list prompt, then each translation still goes
through the normal per-sentence verify/correct loop individually) rather than
re-deriving it by hand next time.

## 8. Experiment 2 — longer/more complex sentences, lower temperature

Date: 2026-09-08. Same model (`deepseek-chat`), same prompts/templates (§2), same
`max_iterations=3`, but:
- **32 sentences** instead of 20: the original 20 plus 12 new ones targeting
  constructs the first batch didn't cover — subordinate/conditional/relative/
  complement clauses, negation, and ditransitives (`data/exp2_sentences.txt`).
- **`temperature=0.1`** instead of 0.3, via a new `--temperature` flag added to
  `run_ai_eval.py`'s CLI (threads through to `make_deepseek_fn`/`make_gemini_fn`;
  `loop.py` itself wasn't touched for this).

### 8.1 The 12 new sentences

```
Cuando llueve, los niños no salen a jugar.
Si tú vienes mañana, yo preparo la comida.
Ella sabe que su hermano no trabaja los domingos.
El hombre que vive en la casa grande es mi tío.
Nosotros no compramos el caballo porque es muy caro.
¿Por qué no vienes a la fiesta esta noche?
¿Qué le vas a dar a tu madre para su cumpleaños?
Yo le presto mi libro a mi amigo.
Ellos no les dan agua a los animales.
El profesor le enseña gramática guaraní a los estudiantes nuevos.
Aunque llueve mucho, nosotros vamos a trabajar.
¿Tú le dijiste la verdad a ella?
```

### 8.2 Aggregate acceptance

| Context | Total | 1st-try | Corrected | Overall | Avg iterations |
|---|---|---|---|---|---|
| `none` | 32 | 10 (31.2%) | +5 (15.6%) | **15 (46.9%)** | 2.22 |
| `coq` | 32 | 14 (43.8%) | +2 (6.2%) | **16 (50.0%)** | 2.06 |

The gap the smoke test showed (65.0% vs 90.0%, a 25pp spread) mostly **evaporates**
here (46.9% vs 50.0%, a 3pp spread). One run isn't enough to say why on its own —
see §8.3 for a breakdown that separates "harder sentences" from "lower temperature"
as competing explanations, since this run changed both at once.

### 8.3 Original-20 vs. new-12 subset, within this same run

| Subset | `none` accepted | `coq` accepted |
|---|---|---|
| Original 20 (same sentences as the smoke test, now at temp=0.1) | 11/20 (55.0%) | 13/20 (65.0%) |
| New 12 (harder constructs) | 4/12 (33.3%) | 3/12 (25.0%) |

Two things worth separating:
- **Temperature confound**: even restricted to the *same 20 sentences* as the
  original smoke test, the `coq` advantage shrank from +25pp (65%→90% at temp=0.3)
  to +10pp (55%→65% at temp=0.1). This run cannot tell you whether that's because
  lower temperature narrows the gap, or because it's noise from a single sample —
  a real study needs a temperature sweep, not one before/after data point.
- **New-sentence reversal**: on the 12 new (harder) sentences, `coq` did *worse*
  than `none` (25.0% vs 33.3%). Small n (12), so treat as a hypothesis, not a
  finding — but it's the opposite direction from the headline result, and worth
  checking at scale before assuming grammar-context help generalizes to longer/more
  complex sentences.

### 8.4 PARSE_ERROR vs. real verifier failures (now separated — see §8.6)

| | `none` | `coq` |
|---|---|---|
| PARSE_ERROR (tokenizer/analyzer coverage gap) | 18 | 19 |
| Verifier predicate failures (total) | 38 | 31 |
| — `ss_transitivity_ok` | 24 (63.2%) | 18 (58.1%) |
| — `ss_agree_ok` | 13 (34.2%) | 10 (32.3%) |
| — `ss_hierarchy_ok` | 1 (2.6%) | 1 (3.2%) |
| — `suffixes_ordered` | 0 | 2 (6.5%) |

`PARSE_ERROR` is now roughly as common as (or more common than) genuine grammar
failures in both conditions — for the harder sentence set, the analyzer's parsing
coverage is as much a bottleneck as anything the Coq verifier or the grammar-context
prompt actually influence.

**Structural coverage gap found while reading `verifier.py`**: `_diagnose_adverbial`'s
own docstring notes that `CS_Adverbial` only composes `wf_sentence(main) &&
wf_sentence(subord) && wf_adv_clause(ac)`, and `build_complex_candidates` in
`loop.py` only recognizes adverbial subordinators (`cuando`/`si`/`porque`/
`aunque`-style, via `ADV_SUBORDINATOR_FORM_INDEX`). Relative clauses ("el hombre
**que** vive...") and complement clauses ("sabe **que** su hermano...") have no
candidate-builder at all — there's no code path that can represent them, so
sentences using them fail (usually with `PARSE_ERROR`) regardless of translation
quality or context mode. Both conditions failed on "El hombre que vive en la casa
grande es mi tío." for exactly this reason. This is a real gap in what the pipeline
can currently *verify*, not a signal about context mode — flagging it here rather
than silently letting it dilute the ablation.

## 9. Experiment 3 — raw translation only, correctness judged manually (no Coq verifier)

§6 and §7.1 above flagged the core risk with every result so far: the Coq verifier
only judges grammatical well-formedness, never whether the Guaraní actually means
the Spanish sentence, so an "acceptance rate" can go up while translation quality
doesn't (or gets worse). This experiment removes the verifier from the loop
entirely so you can judge correctness yourself, instead of trusting the automated
signal.

### 9.1 New code: `guarani/run_raw_translate.py`

A new, separate entry point — **imports nothing from `verifier.py` or
`analyzer.py`, and never calls the correction loop.** For each sentence it does
exactly one LLM call per context mode (no iterations, no accept/reject, no
`predicate_history`) — it reuses `loop.py`'s existing
`TRANSLATION_PROMPT_TEMPLATE`/`CONTEXT_PROMPT_PREFIX_TEMPLATE`/
`load_coq_context_once()` so the prompt text is identical to what `run_ai_eval.py`
sends, just without anything downstream judging the result.

Two outputs:
- A flat JSONL log (`--output`): `source_sentence, model_name, context_mode, output`.
- A **blind** side-by-side review CSV (`--review-csv`, via the new
  `export_review_csv()`): one row per sentence, `output_a`/`output_b` with
  column order randomized per row and which condition is which hidden in an
  `a_is_coq_context` column — the same blinding pattern `analyse_results.py`'s
  existing `export_rating_csv()` already uses for human raters, so you can rate
  correctness without knowing which output came from which condition until you
  decode it afterward. `correct_a`, `correct_b`, and `notes` are left blank for
  you to fill in.

### 9.2 Run

Same sentence set as Experiment 2 (`data/exp2_sentences.txt`, 32 sentences, for
direct comparability), same model and temperature:
```
python -m guarani.run_raw_translate \
  --sentences data/exp2_sentences.txt \
  --models deepseek-chat \
  --temperature 0.1 \
  --output results/exp3_raw.jsonl \
  --review-csv results/exp3_review.csv \
  --rate-limit-delay 0.5
```
64 translations total (32 sentences × 2 context modes), all deepseek-chat.

### 9.3 Deliverables

- **`results/exp3_raw.jsonl`** — 64 rows, flat log, no verifier fields.
- **`results/exp3_review.csv`** — 32 rows, ready for you to fill in `correct_a`/
  `correct_b`. To decode after rating: `a_is_coq_context=True` means `output_a`
  is the `coq`-condition translation; `False` means `output_b` is. Group your
  ratings by that column the same way `analyse_results.py` groups by
  `context_mode` to get a manual correctness rate per condition, comparable to
  §5.1/§8.2's verifier-based acceptance rates.

### 9.4 One thing worth noticing before you even start rating

Without the correction loop's second/third attempts to paper over a bad first
try, at least one translation is a glaring outright failure: for "El hombre que
vive en la casa grande es mi tío." (the man who lives in the big house is my
uncle), the `coq`-condition single-shot output was just **`túva`** — one word,
meaning "father," not a sentence at all. In Experiment 2 (§8.5), the same Spanish
sentence under `coq` with the correction loop produced "tahýi che rymba'i" →
"Che tahýi rymba'i." instead — different wrong output, not the same one fixed.
Two things follow: (1) even at `temperature=0.1`, repeat calls to what's
supposed to be the same prompt aren't fully deterministic — another argument for
§7.3's "multiple samples per condition" — and (2) the correction loop's 3
iterations clearly aren't just polishing already-decent translations; some of
what it "fixes" starts from a first attempt this broken, which the Coq verifier
has no way to flag as a meaning problem (the loop only stops it from being a
*grammar* problem).

## 10. Fix: relative/complement-clause candidate-builder (closing the §8.4 gap)

Date: 2026-09-08. §8.4 flagged that `loop.py` had no candidate-builder at all for
relative clauses ("the man **who** lives...") or complement clauses ("she knows
**that** ..."), so any Guaraní output using one failed regardless of translation
quality. Investigating turned up better news than expected: **the formal grammar
already fully specifies these** — `rocq/noun_phrases.v` defines `NP_Rel : noun ->
embedded_clause -> guarani_np` and `NP_Comp : embedded_clause -> guarani_np`
(§12–14, `embedded_clause := conjugated_verb`), well-formed iff the embedded verb
carries the `-va` (relative) or `-ha` (complement) nominalizer suffix. `analyzer.py`
even has a real code path for constructing them (`analyze_np_span`, ~line 1119–1150)
— it's just dead code, because `analyzer.py`'s single-token verb analyzer, `analyze()`,
can't parse a `-va`/`-ha`-suffixed form at all (`analyze("oikóva")` → 0 parses,
confirmed directly). `analyzer.py` and `verifier.py` were not touched — I'm not
allowed to fix `analyze()` itself, so the fix lives entirely in `loop.py`:

- **`_analyze_nominalized_verb(token, suffix)`** (new): strips the `-va`/`-ha`
  surface off a token (trying both the accented remainder and its deaccented form,
  since e.g. `oiko` + `va` surfaces as `oikóva` — stress shifts onto the new final
  syllable), re-parses the bare stem with the existing `analyze()`, and reattaches
  the nominalizer suffix to whatever `ConjugatedVerb` comes back. Same
  strip-then-reparse pattern `loop.py` already used for adverbial enclitics
  (`_strip_adv_enclitic`).
- **`_rel_comp_np_candidates(tokens, start)`** (new): rebuilds the `NP_Rel`/`NP_Comp`
  construction `analyze_np_span` already attempts, using the above instead of the
  dead `analyze()` call.
- **`_np_span(tokens, start)`** (new): `analyze_np_span(tokens, start)` plus the
  above — replaces all 4 direct `analyze_np_span` call sites in `loop.py`
  (`_best_np`, and 3 in `build_nonverbal_candidates`), so both plain verbal
  sentences (relative clause as subject/object) and nonverbal/equative sentences
  (relative clause as the whole predicate) pick it up.
- **`_best_np`'s tie-break fixed**: caught during testing — when a rel/comp-clause
  reading ties on token-count with a same-length generic reading (e.g.
  `analyzer.py`'s permissive `gen_noun` fallback happily treats *any* unrecognized
  second token as a possessed noun), the generic one was winning the tie purely by
  being listed first. `_best_np_sort_key` now ranks `rel_clause`/`comp_clause`
  above generic readings (below `exact_pronoun`, which still wins outright) — a
  token that verb-parses with a `-va`/`-ha` suffix is a much stronger, more
  specific signal than a coincidental same-length noun-noun reading.

### 10.1 Verified

Directly, through the real Coq verifier (`coqc`), not just constructed and eyeballed:
- `"Kuimba'e oikóva ohecha peteĩ óga."` ("the man who lives sees a house") — subject
  is a relative clause (`NP_Rel`), `wf=True`.
- `"Che ahecha oguatáha."` ("I see the act of walking") — object is a complement
  clause (`NP_Comp`), `wf=True`.
- `"Kuimba'e oikóva che ru."` as a bare-juxtaposition equative — 9 of the generated
  `NonverbalSentence` candidates use `NP_Rel`, and isolating just those still
  verifies `wf=True` independently.
- No false positives: tokens ending in `-va`/`-ha` that *aren't* nominalized verbs
  (`tuichava`, `táva`, `guahuharã`, `guahurãhá`, `guahuhare`, `guahurehá`) all
  correctly produce zero candidates, since their stripped stem doesn't
  independently verb-parse.

Against the project's own gold benchmark (`data/guarani_benchmark.csv`, via
`run_benchmark.py`): all **6/6** `wf`-expected relative/complement-clause rows
(`rule_NPB7_rel_wf_iff`, `rule_NPB7_comp_wf_iff`, `rule_NPB8_rel_needs_va`,
`rule_NPB8_comp_needs_ha`, `rule_NPQ5_rel_concats_with_verb`,
`rule_NPQ6_comp_is_verb`) now **pass** — e.g. `kuimba'e oguapyva` (`"the man who
sits"`) verifies well-formed, where before this fix it couldn't be parsed at all.

**What's still out of scope, honestly:** the same 6 theorems also have paired
`ill`-expected rows (e.g. `kuimba'e oguapy`, the same sentence *without* `-va`,
expected to fail specifically with `is_rel_clause`) — these still fail, but not
because of anything this fix touches: `_analyze_nominalized_verb("oguapy",
VS_NomVa)` returns `[]` (confirmed directly), so my code contributes zero
candidates either way for an un-suffixed token, exactly as before. `"oguapy"`
without `-va` is just an ordinary, independently-valid verb, so `build_sentence`
correctly parses `"kuimba'e oguapy"` as a plain subject-verb sentence and accepts
it — genuinely well-formed Guaraní, just not what that specific theorem intends to
test. Distinguishing "coincidentally valid plain sentence" from "failed attempt at
a relative clause" needs a purpose-built dispatch that knows the *author's intent*
was a relative clause (i.e. a direct `Compute is_rel_clause cv` test, not an
end-to-end translate-and-verify pipeline) — out of reach from `loop.py` alone, and
out of scope for what was asked.

**Also out of scope, per §8.4's own note:** `embedded_clause := conjugated_verb`
in the Coq grammar — the relativized verb alone, no argument slot. A relative
clause with its own complement ("the man who lives **in the big house**") still
can't be represented; that needs the `.v` files themselves extended, not `loop.py`.

I was not able to run the full 408-row benchmark as a clean regression check — two
attempts were killed by the harness for system-wide low memory (no leftover
`coqc`/`python` processes found afterward, so this looks like host memory pressure
unrelated to the fix, not a leak it introduced). Ran two smaller slices instead: the
12 `NPB7`/`NPB8`/`NPQ5`/`NPQ6` rows above (6/12 pass, all 6 failures are the
pre-existing/out-of-scope `ill` rows just discussed), and the first 60 rows of the
full benchmark as a general regression check (32/60 pass — no way to confirm this
matches the pre-fix baseline exactly, since the git-tracked version of `loop.py` is
a much older, structurally different prototype, not a clean "just before this fix"
snapshot; but the false-positive check above (`tuichava`/`táva`/etc., all
zero-candidate) directly rules out my change as the cause of any of these 60
rows' failures outside the 8 relative/complement-clause-specific ones).
